## P1 会让用户做错事或看到假状态

### P1-1 连续执行面板偷读隐藏的 AI 模型/线程/AI 开关
`process.js:595-596,613-615` 读 `sel-model` / `ck-ai` / `sel-threads`，但这三个控件写在
`process.html:99-106` 的 `data-panel="map"` 里 —— 站在「连续执行」面板时用户看不见也改不了。
确认框 `process.js:604-610` 也没复述 AI 状态与模型名。

→ 把控件提到 split 外面（或复制一份到 all 面板），确认框复述「模型 X · 线程 N · AI 开/关」。

注：与 CLAUDE.md 记载的历史 bug（连续执行偷读②面板的公司勾选框）是同一个病，当时只治好了公司选择那一半。

### P1-2 勾④复查但不勾③清洗时静默不执行，任务标题却承诺执行了
`pipeline.py:307` `if do_audit and scope:`，scope 只在 `do_clean` 时才有值。
`main.py:534-536` 生成的标题仍是「数据处理（映射→复查）」，用户以为复查通过了。

→ 前端勾④时自动勾③或明确提示；或后端无 scope 时退回按 companies 复查。标题不能承诺没做的事。

### P1-3 待办页「只看还有待复核的」复选框无效
`todo.js:22-26` 的 fetcher 闭包读 `onlyPending`，但被包在 `cached("todo:comp:review")` 里；
`todo.js:141` 的 onchange 调 `loadCompanies()`（force=false）命中缓存直接返回，fetcher 不执行。

→ 过滤挪到渲染层，缓存只存未过滤的全量数据。

### P1-4 从总览跳进待办后「全部公司」返回键死循环
`todo.js:177` 每次 `loadCompanies()` 结尾都 `openCompany(PRE_COMPANY)`，
而 `todo.js:131` 的返回键正是调 `loadCompanies()`。带 `?company=X` 进来永远退不回列表。
这条路径是总览「待人工」列的主跳转路径（`overview.js:32-33`）。

→ PRE_COMPANY 改成一次性消费。

### P1-5 总览④复查显示绿色「三项均为 0」，实际 45/51 家从未复查
`overview.js:50-52`。实测 audited=6、audit_unknown=45 仍出绿色 ok 芯片。
违反本项目自定的「三重编码、绝不靠颜色单独表意」。

→ 只有 audit_unknown==0 且 audit_failed==0 才给 ok；有待查一律 stale。

### P1-6 总览轨道 ⑤ 产品数大于 ③（2900 > 2792）
`overview.py:188,194`：`cleaned_products` 只算 clean=="done"，`idmapped_products` 只算 idmap=="done"，
一家 clean=stale/idmap=done 的公司只进后者。在明确宣称「每一段产品数应当对得上」的图上，
最终交付比清洗后还多。

→ 统一口径并在 UI 说明包含关系。

### P1-7 切筛选/点刷新导致已勾选的公司全部丢失
`process.js:218-223`（③）、`564-570`（连续执行）、`286-293`（④）整段重建 tbody，
勾选态只从 preCompany/status 推导。清零后表格看起来完全正常，点运行跑的是默认集合。

→ 三张表各维护一个 `Set<公司名>` 选中态，重建时回填。

### P1-8 流水线页冷启动显示错误空态「没有待处理的公司」
`process.js:735-736`：无缓存时先 `drawAll(true)`，cleanRows=[] → 渲染「没有待处理的公司」，
而真实情况是 58 秒的 `/api/consolidate/status` 还在跑。实测 headless 首访 55 秒超时。

→ 区分「还没读到」与「读到了但是空」；`cleanBusy()` 已存在，启动路径没走它。

## P2 明确的功能/一致性缺陷

### P2-1 一键全流程「指定公司」缓存了一份空列表
`pipeline.js:174-176`：`pInit()` async 未 await，紧接着 `pLoadScope(false)`；
fetcher（`:42-46`）读 `#p-input`.value 时输入框还空 → `{companies:[]}` 写进 localStorage。
此后「指定公司」永远看不到输入目录的新公司。

→ await pInit() 后再画；路径为空时抛错，别让空结果进缓存。

### P2-2 统计页 AI 分析未给模型分类体系分母
`report.py:342` 的导出用了 `_taxonomy_size()`，但 `/api/stats/analyze`（`stats.py:268-281`）没有。
正是 CLAUDE.md 明令禁止的那件事（模型编过"162 个子类"，真值 160）。

→ 复用 `report._taxonomy_size()`，同时喂「完全没有产品的一级分类」。

### P2-3 统计页 KPI「覆盖的二级分类 124」没有分母
`stats.js:74`。应显示 `124 / 160`。与 P2-2 同源：只在喂 AI 时贯彻了，没贯彻到界面。

### P2-4 统计页冷启动 94 秒白屏、零加载提示
实测首开 1 分 34 秒。`stats.js:112-116` 只置灰按钮，无骨架无提示。
全站其他慢列表都有 `cached()` + "读取中…"，唯独这里漏了。

→ 加载态占位；考虑给 `/api/stats/dist` 加服务端缓存或改后台任务。

### P2-5 「缓存口径」显示成绿色 ok 芯片
`stats.html:26` 写死 `class="chip ok"`，`stats.js:119-120` 只换 innerHTML。形状与颜色打架。

### P2-6 待办页首次真实拉取被标成「（缓存）」
`todo.js:174` 传 `!force`，而默认 force=false。空 localStorage 的截图显示"读取于 17:23（缓存）"可反证。
一个用来建立信任的时间戳在说谎。

→ 从 `cached()` 的 onData 拿正确的 fromCache；其余用 cached 的页面对照检查。

### P2-7 分类树「搜索」会吃掉「只看新增」
`taxonomy.js:17-19`：`if (q)` 直接覆盖 onlyNew 的结果，两条件无法取交集。→ 改链式过滤。

### P2-8 统计页出现两个同名的「查看数据表」
`stats.js:155-157` 同一容器塞了两个 dataTable，summary 都叫"查看数据表"。
→ 给 `dataTable()` 加标题参数。

### P2-9 同名变体判定集合，总览与变体卡不一致
`overview.py:157`（映射输出 ∪ 未匹配 ∪ 过程记录） vs `variants.py:74-78`（映射输出 ∪ 未匹配 ∪ 清洗后）。
两者并排显示在同一页。→ 统一走 `variants._all_companies()`。

### P2-10 无并发闸门（建议单独做一次）
后端不做同 kind 互斥，前端按钮又是 POST 返回后才 disabled（`process.js:625-629`）。
双击运行或开两个标签页 = 两个线程写同一棵输出树，没有任何一层拦得住。
在一个以「数据零丢失」为最高约束的产品里，这是唯一没有防线的位置。

→ ① 路由层按 kind 拒绝重入（冲突返回 409 + 现有 job_id）；② 前端点击瞬间禁用。

## 本轮新增的两条（用户当场提出，已修）

### N-1 总览「公司 × 阶段」全部铺开，没有滚动窗口
公司数已经涨到 95，整表铺开会把页面拉成一条长带，阶段轨道和待办卡全被顶出屏幕。
→ `index.html` 把表包进 `.tablebox.matrix`，`style.css` 给它
`max-height:clamp(380px,calc(100vh - 300px),760px)`，表头 sticky 跟着停在顶上。

### N-2 新爬到的公司在总览里根本不显示
根因：`overview.build()` 的公司集合是「映射输出 ∪ 未匹配 ∪ 过程记录」，**完全没有输入目录**，
而这三处都要等映射跑完才有内容。所以新公司必须先跑一次全流程、再点刷新才看得见 —— 那时候活都干完了。

→ 三处改动：
1. `build()` 并入 `_input_index(cfg)`，新增 `in_input` / `input_products` 两个字段，
   ② 映射列多一个 `stale`（源数据变过）状态。
2. `GET /api/overview` 与 `/badge` 顺手调 `overview.sync_input()`：只 listdir 比对名字，
   仅对缓存里没有的公司现场数一次产品数（预算 8 家），**实测 0.12 秒**，秒开不受影响。
3. 总览首屏多一档 IN「N 家待映射」+ 待办卡 + 「待映射」筛选；`needs_attention` 把它算进徽标。

⚠ 性能上有个坑，改这里务必注意：输入目录已经指到 `/mnt/d/已审核数据`，
**87 家 / 10573 个产品，全量 walk 要 97 秒**。所以
`build()` 才做全量核对；`refresh(names)` 只能走 `_input_index_for(cfg, names, known)`
（只查这几家）；秒开路径只走 `sync_input`（只 listdir + 数新公司）。
把这三条路径中的任何一条换成全量 walk，页面就会卡死。

# 2026-07-29 结构性改版（批次 0 / 1 / 2 / 3）

## 批次 0 · 产品判定重写
`backend/products.py` 是唯一口径：**产品 = 叶子目录（无子目录）且含至少一个产品性文件
（json / pdf / 图片）**。替换掉原先散在 8 个模块的 5 套判据。

根因：`run_mapping` 用 `glob("**/info.json")` 发现产品 —— 没有 info.json 的产品
**从第②步就被静默丢掉**。实测「杭州利珀科技股份有限公司」info.json 数为 0，
`scan_companies` 的 `if n:` 把它整家跳过，它在界面上根本不存在（实有 8 个产品）。
分类口径补一条：**压根没有 json → 类别3**（类别3 的语义是"参数不在 json 里"）。
装 `.py/.pyc` 的叶子目录是爬虫脚本残留，不算产品。

⚠ `is_product_files` 会被调用几万次，写法要抠：短路 + 集合查扩展名。
写成 `.lower().endswith(十元组)` 实测把全量扫描从 94 秒拖到 346 秒。

## 批次 1 · 总览动作化，流水线页删除
动作挂在公司上而不是步骤上。`overview.js::nextAction` 是全页唯一判定，
矩阵每行一个「下一步」，档位上的「一键」＝把这一档所有公司的下一步批量做掉。
②③④⑤ 四列收成一个进度列（点 ② 看映射报告、点 ④ 看复查明细）。
默认档「要处理的」，走完全程的收起来。

「走完全程」与「无源可处理」必须分开 —— 一家只在 `_未匹配`/过程记录里露过面的公司
跑不了任何一步，但那不等于它做完了。

流水线页归档到 `frontend/_archive/`（**本项目不在 git 下，所以不硬删**）。
路径与 AI 设置 → 设置页（`js/cfgpaths.js`）；id 解析 → 总览抽屉（`js/ovid.js`）。
导航 7 项 → 6 项。

写盘任务改成**串行队列**（`jobs.py::submit` + `/api/queue`），不再 409 拒绝；
队列条带可展开的增量日志。

⚠ `jobs._execute` 里 **on_done 跑完才对外宣布 status=done**。以前先置 done 再跑钩子，
而钩子正是"把状态刷进总览缓存"，前端一看到结束就去重拉，拿到的还是旧快照 ——
"跑完了状态却没变"就是这么来的。

## 批次 2 · 搁置 + 输入级变体
`backend/shelf.py`：把归不了类的未匹配产品标记掉，不再计入待办。
**产品级、可撤销、数据原地不动**（仍留在 `_未匹配` 里）。
没有这个出口，「已走完全程」这个终态不可达。

`variants.detect_input(cfg)`：输入目录里就重名的，在进流程之前发现（只 listdir 比基名）。
按用户定的规矩**只报不动**，合并由人工在资源管理器里做。

`overview._ghosts()`：只剩「过程记录」残留、实际已无任何产品的公司要剔掉。
过程记录不会跟着公司目录一起消失，`review.list_companies` 只看这份记录，
于是被删掉的同名变体会以「0 产品 + N 待复核」永远挂在总览和待办徽标上。
实测清掉 4 家、369 条死的待复核记录。

## 批次 3 · 自包含 HTML 报告
`backend/htmlreport.py`：一个 `.html` 文件，双击就能看，**筛选/下钻/图表联动与统计页一致**，
零外部请求。选它而不是 Excel 透视表，是因为 openpyxl 生成不了可靠的透视表/切片器，
而且透视图里守不住本项目的图表约束（横向条形、绝不饼图/双轴、7 色上限）。
xlsx 导出保留，两个入口并存（`format: html|xlsx`）。

⚠ `htmlreport.CSS` 里有大量 `%`（100%/40%），**不能用 % 格式化**，只能占位符替换 ——
写成 `CSS % PALETTE[0]` 会让整个后端起不来。

⚠ 导出的实时扫描**必须放在后台任务里**，放在请求里前端必然超时、连 job_id 都拿不到。

## 一个卡了 6 天的死循环（顺带修掉）
`consolidate` 清理孤儿产品时只看上次的记忆 `products_map`，而旧版记忆没有这个字段（空的），
于是一个孤儿都找不出来；校验又要求「落地数 = 分类数」，孤儿让校验永远过不去，
不写清洗记忆 → 公司永远停在「需重跑」，重跑多少次都一样。
实测「英福康」247 个产品的输出里多了 1 个换过分类的旧副本，卡了 6 天。
**改成以输出目录的实际内容为准**找孤儿，不依赖记忆。修复后一次跑通：
清掉 1 个孤儿 → 校验 ✓ → 复查 0/0/0 → 状态流转到「已走完全程」。
